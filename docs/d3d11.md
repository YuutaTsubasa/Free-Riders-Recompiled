# Direct3D 11 (experimental)

Issue #359: PCs whose GPU has neither a Vulkan nor a D3D12 driver on Windows
(Intel HD 4000/4600 and others of that age) cannot run the game. Their
drivers do have Direct3D 11 at feature level 11_0. This is the first phase of
a backend for them: does the game reach its title screen on D3D11, and how
much is left.

Run it with `SFR_GRAPHICS=d3d11` (the launcher's Display > Graphics backend >
"Direct3D 11 (experimental)"), Windows only.

| Setting | Effect |
| --- | --- |
| `SFR_D3D11_FEATURE_LEVEL=11_0` | Make the device at 11_0 even where 11_1 exists (as an HD 4000 has it). |
| `SFR_D3D11_WARP=1` | Draw with Windows' software rasterizer (WARP) instead of the GPU. |
| `SFR_D3D11_DEBUG=1` | The D3D11 debug layer (needs Windows' Graphics Tools). |
| `SFR_D3D11_SHADER_CACHE=<dir>` | Where compiled shaders are kept (default `<runtime shader cache>/d3d11`). |
| `SFR_D3D11_PREWARM=0` | Do not compile shaders on background threads as the game creates them. |
| `SFR_D3D11_TRACE=<n>` | The n-th submission with draws logs each draw's state and samples written (`D3D11_TRACE`). |
| `SFR_D3D11_INVERTED_DEPTH=1` | Experiment: hand D3D11 the title's inverted viewports instead of flipping depth in a geometry shader. |

## How it is put together

- **Plume backend** (`src/plume_d3d11.h`, `.cpp`): the port's own, beside the
  pinned Plume, implementing what the renderer and presentation use. Command
  lists record draws and bindings as plain data (the rest as callbacks) and
  are replayed on the immediate context at submission. The replay keeps what
  the context has bound and calls D3D11 only for what changed (most of a
  draw's 48 views and 16 samplers are those of the draw before); views are
  forgotten whenever the render targets change, as binding a target unbinds
  views of it. Upload buffers are CPU memory with GPU copies: the merged
  ranges a submission's draws read are copied up once before it replays
  (constants on into a second, constant-buffer copy bound with D3D11.1's
  `*SetConstantBuffers1` offsets). The renderer's kept vertex and index
  buffers, filled once and kept mapped, are marked `writeOnce` and copied up
  only at their first use. Copies into textures from upload memory are
  `UpdateSubresource`; readbacks map a staging texture at once. Fences are
  event queries. `NATIVE_D3D11_REPLAY` logs, every 600 submissions that
  draw, the CPU time of submission (median, p95), the part spent copying up,
  the bytes copied and the binding calls made and skipped.
- **Renderer**: the D3D12 layout (constants as root descriptors b0..b4, one
  texture heap) with one change: each draw binds 16 2D, 16 2D-array and 16
  cube textures and 16 samplers (t0-t47, s0-s15) from the heap slots its
  shared constants name (`D3D11CommandList::setXenosTextures`), well inside
  D3D11's 128 views and 16 samplers a stage. No survey UAV.
- **Shaders** (`src/d3d11_shader_source.h`): the translated HLSL's D3D
  branch, rewritten for shader model 5.0 and compiled at run time with
  Windows' own `d3dcompiler_47.dll` (FXC), per pipeline for the alpha-test
  specialization, kept on disk. Shader model 5.0 indexes resource arrays only
  with literals, so each fetch constant reads element *s* of the arrays above
  (its descriptor index becomes the literal *s*); FXC refuses `continue` in a
  `switch`, so XenosRecomp's dispatch loop becomes guarded blocks in case
  order. All 468 shaders of a full play-through's cache compile
  (`sfr_d3d11_shader_source_test <out/shaders/runtime>`). Each shader starts
  compiling on a background thread (up to 4, below normal priority) when the
  game creates it, as a level loads, at specialization 0; a pipeline that
  needs it waits for that compile instead of starting another.
- **Inverted viewports**: depth is flipped in the geometry shader D3D12 uses
  without `InvertedViewportDepthFlipsZSupported`. The backend's own shaders
  (blit, overlay, model, depth flip) are compiled to DXBC at build time with
  the Windows SDK's FXC.

## What D3D11 lacks, and how each is met

| Vulkan / D3D12 | D3D11 here |
| --- | --- |
| Bindless texture heap (descriptor indexing) | 48 textures + 16 samplers bound per draw, literal indices in the shaders |
| Push constants / root constants | A small constant buffer per push range, updated whole |
| Root CBVs at any offset | `*SetConstantBuffers1` windows of 4096 constants, 256-byte aligned (D3D11.1 runtime and driver) |
| Persistently mapped upload heaps | CPU memory + per-submission copies |
| Specialization constants / DXIL linking | A macro, one FXC compile per value |
| Component swizzles in views | Only the renderer's all-zero null views, made from zeroed RGBA8 textures |
| Clear of part of a depth target | A depth-only full-screen triangle per rectangle |
| Clip distance, geometry shaders, BC formats | Native in shader model 5.0 / feature level 11_0 |
| Explicit barriers, render passes | Not needed: the runtime tracks hazards |
| Triangle fans | Not used (the renderer converts them, as for D3D12) |

## Status (phase 1, 2026-11-10)

Measured on an RTX 4090 (driver 32.0.16.2101) and WARP, i9-14900KF, the
release check's scripted inputs (`race.env`), 1280x720:

- Title screen: the same picture as Vulkan's at present 1000, 2000 and 3000
  (about 1% of pixels differ, all in the animated streaks and the START ring)
  at feature level 11_1, at 11_0, and on WARP.
- The menus, the course and a Dolphin Resort race to present 17000 draw
  without a crash or a failed shader (151 shaders, 248 pipelines); the race
  frame matches Vulkan's apart from where the racers are.
- A race frame: ~680 draws, 16.7 ms paced at 60 fps; replaying the lists at
  submission takes 8.8 ms of CPU (median), the cost to cut first for slow
  laptop CPUs.
- First use of a shader compiles it (median 355 ms, longest 2.5 s), then it
  is on disk.

## Status (phase 2, 2026-11-11)

Same machine and inputs, plus `SFR_TEST_RAND_SEED=1 SFR_PARALLEL_WORKER=0
SFR_REALTIME_UI=0` so that two runs reach the same screens at the same
presents; screenshots every 500 presents from 1000 (race from about 14330).

- Correctness: two first runs (both compiling their shaders), Vulkan and
  D3D11 11_1, gave the same picture bit for bit at all 27 presents from 1000
  to 14000 (title, menus, course select, loading). Runs with warm caches
  differ in what the game times by the clock (the chao's flight, a sparkle,
  when a panel opens; two D3D11 runs differ the same way), and are otherwise
  identical. Races do not repeat (the racers' places differ from the
  countdown, docs/performance.md); side by side to present 24000 (lap 2,
  2:19) every effect, the HUD, sky, glow and motion blur are drawn alike.
- Submission CPU on a race frame (~800 draws): median 10.4 ms before,
  2.2-3.3 ms after (p95 4.3-5.0 ms), 1.6-2.3 ms of it copying up 15-20 MB.
- First run with an empty DXBC cache: a race stalled 113 s in 14 frames
  (longest 31 s) before, 0.8 s in 2 frames (longest 0.43 s) with background
  compiles; a second run compiles nothing and stalls no frame.
- FXC: its optimization levels make no difference in time or output here;
  `D3DCOMPILE_SKIP_OPTIMIZATION` compiles 3.6 times faster but makes DXBC half
  again as large, which an HD 4000's driver would have to make up for, so
  it is not used.
- The D3D11 debug layer is not installed on this PC (Graphics Tools, an
  optional Windows feature); not run.

Not yet done: DXBC in `shaders.pack` and a D3D11 pipeline manifest (a first
run on a player's PC still compiles every shader once, on background
threads), the release check's D3D11 case, real Intel HD 4000/4600 hardware,
and a way round drivers without constant buffer offsets (expected of WDDM
1.2 and later drivers, unconfirmed on an HD 4000; the backend refuses to
start without them and says so in game.log).
