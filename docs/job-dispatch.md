# 工作分派與 R6025（載入偶發崩潰）

## 原本的機制

工作分派 `823B5D40`（每格由 job system 呼叫）會：

1. 把工作項目放進無鎖佇列（`'LfQu'`：`82750B30` 判空、`82750C40` 取出）；
2. 喚醒三條輔助執行緒 `823B60C0`（處理器 1、4、5）；
3. 自己也一起消化佇列；
4. `WaitForMultipleObjects(3, done, TRUE, 16 ms)`，**不看結果**；
5. 走過 `+516` 的串列，把每個項目重設（`+160` 清旗標、`memset(+176, 0, 320)`、`+496 = 0`）後重用。

消化迴圈（`loc_823B5E30`，輔助執行緒的版本在 `loc_823B60E4`）取出項目後：

```
lwz  r11,168(r3)      ; 工作項目的函式
cmplwi cr6,r11,0
beq  cr6,<next>       ; 只擋 0
addi r4,r3,64
lwz  r5,520(r3)
mtctr r11
bctrl
```

## 症狀

`+168` 只擋 0，擋不住「C++ 基底類別的 pure virtual 欄位」。當那個欄位是純虛擬的
placeholder 時就會呼叫到 CRT 的 `sub_82A53BC0`（R6025），遊戲把它變成 `KeBugCheck`
而整個停住 —— 就是「Grand Prix 大約四次載入壞一次」的那個崩潰。

`SFR_THREAD_START_DELAY_US=0`（關掉 2 毫秒的執行緒啟動延遲）可以穩定重現：8 次裡有 2
次停住。停住當下把該項目印出來，`+168` 在 500 毫秒後變成 **0**，代表項目不是「還沒
建好」，而是**已經被第 5 步重設掉了**：分派器的等待逾時後就重用項目，而晚被喚醒的
輔助執行緒還在消化佇列。

（主機上不會發生：輔助執行緒一定在 16 毫秒內做完。這裡的輔助執行緒比較慢，還要等
執行許可，`824D0B10` 的修補已經把逾時從 16 毫秒放寬到 `SFR_WORK_SHARE_WAIT_MS`，
預設 1000。）

## 修補

`src/game_patches.cpp` 攔截 `sub_82A53BC0`，只處理那兩個呼叫點（`lr` 為 `0x823B5E88`
或 `0x823B6144`）：

- 先在**不持有執行許可**的情況下等最多 `SFR_JOB_READY_WAIT_MS`（預設 20）毫秒，讓
  還在建構這個項目的執行緒把 `+168` 填完；填好了就照常呼叫它。
- 還是空的（已經被重設）就**跳過這個項目**直接返回 —— 分派器本來就已經當它做完了。
- 兩種情況各自計數，前 8 次會印 `GAME_PATCH job_filled_in_late` /
  `GAME_PATCH job_skipped_after_reset`。

其他地方的 pure virtual 呼叫仍然交給原本的處理器（那是真的錯誤）。

2 毫秒的啟動延遲仍然保留（它讓這件事一開始就很少發生），但延遲多少才夠取決於主機
速度，手機慢得多，所以需要這個兜底。

## 驗證

| 條件 | 修正前 | 修正後 |
| --- | --- | --- |
| Free Race，`SFR_THREAD_START_DELAY_US=0` | 3 次裡 2 次停住（R6025） | **8/8 跑完**（3 次用到救援） |
| Grand Prix，`SFR_THREAD_START_DELAY_US=0` | 6 次裡 1 次停住（callback 讀到空指標） | **6/6 跑完**（2 次用到救援） |
| Grand Prix，預設設定 | 約四次載入壞一次 | **6/6 跑完，完全沒用到救援** |

預設設定下救援一次都沒觸發，所以沒有額外成本；`GAME_PATCH job_skipped_after_reset`
與 `job_drain_wait` 的次數可以當作「排程相關的改動有沒有讓情況變糟」的指標。

## 還沒解開的部分

失敗時取出的物件位址落在**輔助執行緒 context 的區段**（`ff6xxxxx`），而正常 job 在
`f8xxxxxx`，所以更可能是佇列交出了一個不屬於它的指標，而不只是「被重設的 job」。
`SFR_JOB_TRACE=1` 會印出兩個分派呼叫點每次取出的內容。正常 job 的 `+176..+496` 本來
就是 0，所以那段無法用來判斷。

## 2026-09-26：現在重現不出來了

用[無人看管的比賽腳本](race-controls.md)重跑當初的重現條件
（`SFR_THREAD_START_DELAY_US=0`，也就是把那個藏住問題的 2 毫秒啟動延遲關掉）：

| 條件 | 趟數 | 用到救援 | 卡住 | 結果 |
| --- | ---: | ---: | ---: | --- |
| Free Race | 6 | **0** | 0 | 全部跑到比賽 |
| Free Race，`SFR_COMPLETION_SUSPEND_HANDOFF=0` | 3 | **0** | 0 | 全部跑到比賽 |
| Grand Prix 載入 | 1 | **0** | 0 | 跑到比賽 |

當初記的是「Free Race 8 趟有 3 趟用到救援、Grand Prix 約四次載入壞一次」。
**那組數字現在不成立**，中間隔了 memory barrier、job reset 延後、開場漏喚醒
（round4）等等改動。

第三列是為了測「是不是 round4 的漏喚醒修正順手解掉了根因」——把它關掉之後
一樣零次，所以**不是它**。

### 這代表什麼，以及不代表什麼

**不代表根因已經解決。** 沒有人指出過那行程式碼，只是在這台機器、這條路徑上
不再發生。這個 bug 本來就是時序競爭，而這台 PC 比手機快很多；文件開頭那句
「沒有一個固定的延遲對每台主機都對」仍然成立，所以救援要留著。救援不觸發時
成本是零（它只在偵測器真的拿到純虛擬函式時才等）。

**修正一條先前的推論。** 舊筆記說失敗時取出的物件落在 `ff6xxxxx`，而正常 job
在 `f8xxxxxx`，因此「更可能是佇列交出了一個不屬於它的指標」。`SFR_JOB_TRACE=1`
的實際輸出顯示**正常 job 的 `+164` 與 `+520` 本來就指向 `ff6xxxxx`**
（例如 `a4:ff662120`、`208:ff65bc30`，那是 job 的 context 欄位）。所以那個推論
站不住：`ff6xxxxx` 是 context 的正常位置，失敗時拿到它比較像是把 job 的欄位值
當成了 job 本身，或讀到已被回收、欄位已被覆寫的 job。

另外，`+168`（callback）為 0 的 job 在正常情況下很常見（分派器自己會跳過），
所以「callback 為零」不是異常的判準；真正異常的是 callback **等於純虛擬函式
位址 `0x82A53BC0`**。

### 要再追下去的話

在這台機器上用觀察法已經沒有東西可看。可行的方向是：在**慢的機器**上重現
（手機最有機會，而且那正是救援存在的理由），或是不靠重現、直接從
`823B5D40` 與 `823B60C0` 的程式碼證明那個視窗——後者不需要運氣，但要讀完
整個佇列與 reset 的邏輯。

## 第二個工作池：比賽中的空賽車手欄位（Issue #64）

比賽每格的更新（`824A00C8`）依序走過一串階段；標成平行的階段交給分派器 `8249F048`：

1. 把該階段的工作放進佇列 `0x83E52CD0`（`827507F8`）；
2. 喚醒三條工作執行緒 `8249EF00`（`824D0108`）；
3. 對每條執行緒的 done 事件各呼叫一次 `WaitForSingleObject(event, 16 ms)`（`824D0150`，
   `0x8249F108` 的 `li r4,16`），**不看結果**；
4. 返回，`824A00C8` 立刻在主執行緒上做下一個階段。

工作執行緒在佇列空了、而且自己手上的工作返回之後才設 done 事件，所以等待逾時就代表
還有工作在跑，主執行緒卻已經進入下一個階段。這個池裡的工作包括 `82327CF8` 與
`82326518`：它們走過工作物件 `**(this+192)` 上的賽車手清單（數量在 `+496`，最多讀十筆；
每筆 32 位元組，從 `+192` 開始，`+4` 指向賽車手，狀態在賽車手 `+156`）。兩份 4 核心
PC 的當機記錄（course 7 與 course 1，都在比賽中）都是其中一筆是空的，讀到 `0x9c`。

修補（`src/game_patches.cpp` 攔截 `sub_824D0150`，`lr` 為 `0x8249F114` 且逾時 16）：
等待改成 `SFR_RACE_JOB_WAIT_MS`（預設 1000；16 是原本的值），逾時會印
`GAME_PATCH race_job_wait_timeout`。

在這台 PC 上，限制成 4 個邏輯處理器時，原本的 16 毫秒在一場比賽裡也會逾時 1 到 2 次；
改成 1000 毫秒後沒有逾時，比賽速度不變（12600 到 15900 格，兩種各兩次都是 55.0 秒，
也就是 60 fps 上限）。這裡沒能重現空欄位本身（把等待縮到 1 毫秒也沒有），所以「逾時
後主執行緒的下一個階段改到清單」這一步是推論，還沒有直接觀察到。

`SFR_WATCH_RACERS=1`（需要 `SFR_DIAGNOSTIC_ENTRIES`）在這兩個讀取函式進入時檢查清單：
清單內容變了就印 `RACER_LIST`，數量內有空欄位就印 `RACER_LIST_HOLE`，在分派器之外執行就印
`RACER_JOB_OUTSIDE_WAIT`。

## 第二個工作池：主執行緒自己做工作（Issue #176，`SFR_MAIN_HELPS_JOBS`）

`8249F048` 把工作放進佇列、喚醒三條工作執行緒 `8249EF00`（主控台處理器 0、1、3）之後，
主執行緒**自己一件也不做**，只依序等三個 done 事件。所以每一格比賽主執行緒都要等最慢的
那條工作執行緒做完：手機若把工作執行緒放在慢核心，主執行緒就算在最快的核心上也只能空等。

先量時間花在哪裡（`SFR_WAIT_TRACE=1`，加上這次新增、每 600 次分派印一行的 `RACE_JOBS`）。
在 AYN Thor 上用 `SFR_TEST_WORKER_CPUS=7` 把所有工作執行緒限制在小核心（模擬 #176 的
Pixel 10a），Dolphin Resort 自由賽：

| 主執行緒每格比賽在等什麼 | 毫秒 |
| --- | ---: |
| `8249F048` 等工作執行緒（第一個事件吸收了幾乎全部，因為三個是依序等的） | 6.1 |
| 我們自己的碰撞批次等待（#153，`collision_batch`） | 0.4 |
| 其他（critical section、`nt_all` 等） | < 0.3 |

主執行緒的 `main_blocked` 是 7.0 毫秒；比賽只跑到實際時間的 0.61 倍。所以時間確實花在
「等工作執行緒」，而且不是等某個核心許可：`SFR_PARALLEL_WORKER=all`（預設）下 guest
執行緒各自自由執行，處理器 0 的工作執行緒和主執行緒本來就同時跑。

### 修補

主執行緒在第一次等待之前，用工作執行緒迴圈本身的呼叫（`82750B30` 判空、`82750C40` 取出、
工作的第二個虛擬函式）自己從佇列取工作來做，直到佇列空了才去等。工作執行緒同時也在取；
佇列空了它們照舊發出 done 事件並暫停自己，三個等待維持原樣，所以「等待返回時所有工作都已
做完」這件事不變。主執行緒是以處理器 0 的身分執行工作，和它自己那條處理器 0 的工作執行緒
相同，工作不會看到它原本看不到的處理器。

`SFR_MAIN_HELPS_JOBS`（預設開啟，`0` 關閉；在啟動器的 Test options「處理器」裡）。

### 結果

同一個 APK／執行檔，只切換這個開關（Thor 是 `CLAUDE_INPUT=kicks` 的移動中比賽，
畫格 14000–20500 的平均）：

| 情況 | 關 | 開 |
| --- | --- | --- |
| Thor，工作執行緒在小核心：比賽速度（實際時間的倍數） | 0.61 / 0.62 | 0.78 / 0.85 |
| 同上：`main_blocked` | 7.0 / 7.0 毫秒 | 4.0 / 4.2 毫秒 |
| 同上：主執行緒花在 `8249F048` 的時間（自己做工作＋等待） | 6.1 / 5.9 毫秒 |
| 同上：畫格間隔 | 29.3 / 29.1 毫秒 | 22.7 / 20.2 毫秒 | 3.4 / 3.9 毫秒 |
| Thor，預設核心配置：`main_blocked` | 1.7 / 1.5 毫秒 | 0.7 / 1.0 毫秒 |
| 同上：主執行緒花在 `8249F048` 的時間 | 0.95 / 0.93 毫秒 | 0.76 / 0.76 毫秒 |
| Windows（i9，60 fps 上限）：主執行緒花在 `8249F048` 的時間 | 0.40 / 0.41 毫秒 | 0.33 / 0.34 毫秒 |

（Windows 的 `main_blocked` 含 60 fps 上限的節拍等待 `frame_cap`，所以這裡看 `RACE_JOBS`。）
主執行緒大約做掉一半的工作（Windows 與 Thor 每格約 40 件中的 20 件；小核心情況 38 件中
的 32 件）。Thor 預設配置與 Windows 本來就跑滿 60 fps，所以差別只在主執行緒多出的餘裕。
小核心情況的 `HOST_THREADS undrawn_ms` 兩邊都約 15.5–16 毫秒，看不出差別：開啟後比賽追得
開啟後 frameskip 跳過繪製的格數變多（每 120 格畫 99–105 格，關閉時 117 格），兩邊的未繪製
格不是同一群，所以比較時看比賽速度與畫格間隔。

開啟後小核心情況剩下的等待（`SFR_WAIT_TRACE`）：碰撞批次 1.6 毫秒（主執行緒更早到達下一
步，而批次 `823B5D40` 和它的輔助執行緒還在小核心上跑）、工作之間的 critical section
`0xe7603d04`（`82230720`、`822309fc`）1.2 毫秒，以及等工作執行緒手上最後一件工作 0.9
毫秒。前者是下一個可以讓主執行緒幫忙的地方（同一種作法用在 `823B5D40` 的佇列，但那裡有
job lifetime 與 R6025 的救援要一起顧）。

## 碰撞批次：主執行緒等待時自己做工作（Issue #176，`SFR_MAIN_HELPS_COLLISION`）

#153 的修正讓比賽步進 `8249F048` 先等上一格開始的碰撞批次 `823B5D40` 做完。這個批次在
自己的 guest 執行緒上跑（主控台處理器 3），三條輔助執行緒 `823B60C0`（處理器 1、4、5）
一起消化它的佇列，然後它等輔助執行緒、重設項目、最後自己一條執行緒做物體兩兩配對。
新增的 `COLLISION_BATCH` 行（跟 `RACE_JOBS` 一起，每 600 次分派一行）把一個批次拆成
三段：`drain_ms`（開始到它自己把佇列消化完）、`pairs_ms`（等完輔助執行緒之後：重設與
配對），`batch_ms` 是全部。

| 每個批次（毫秒） | `batch_ms` | `drain_ms` | `pairs_ms` |
| --- | ---: | ---: | ---: |
| Windows（i9） | 2.0–2.3 | 1.8–2.0 | 0.2–0.5 |
| Thor，預設核心配置 | 4.3–5.0 | 3.8–4.2 | 0.4–0.8 |
| Thor，工作執行緒在小核心（`SFR_TEST_WORKER_CPUS=7`） | 10.7–11.7 | 9.1–9.7 | 1.2–2.3 |

時間大多花在消化佇列（每個批次一兩百件小工作），所以主執行緒在等待時改用輔助執行緒
迴圈本身的呼叫（`82750B30` 判空、`82750C40` 取出，再以 `job+64` 與 `+520` 的值呼叫
`+168`）自己取工作來做：

- 只在批次第一次判空（`0x823B5E10`）之後、它自己消化完（到 `0x823B5E9C` 的等待）之前
  取；批次結束時一律關閉。
- 和輔助執行緒一樣，從判空之前到工作返回為止都持有一個 helper lease，所以批次在
  `work_share_wait_done` 等它，不會重設主執行緒手上的工作；拿不到 lease（有刪除在等）
  就只等待。
- 呼叫時 `lr` 設成輔助執行緒的返回位址 `0x823B6144`，半建構工作的 R6025 救援
  （`82A53BC0`）照樣適用。
- 主執行緒是處理器 0；批次的工作原本在處理器 1、3、4、5 上跑。看過的工作函式
  （`SFR_JOB_TRACE=1` 會印 `COLLISION_JOB_CALL`，例如 `82328908`）只用自己的參數與堆疊，
  不讀處理器編號。
- 等待本身不變：比賽步進仍然要等到批次結束（`idle`）才開始，#153 要的順序不受影響。

`SFR_MAIN_HELPS_COLLISION`（預設開啟，`0` 關閉；啟動器 Test options「處理器」）。

### 結果

同一個 APK／執行檔只切換這個開關（Dolphin Resort，`CLAUDE_INPUT=kicks`，Thor 取畫格
14000–20500 的平均）：

| 情況 | 關 | 開 |
| --- | --- | --- |
| Thor 小核心：`collision_wait_ms`（每次分派） | 5.28 / 5.69 | 2.51 / 2.62 / 2.92 |
| 同上：`main_blocked` | 6.87 / 7.36 毫秒 | 4.10 / 4.14 / 4.35 毫秒 |
| 同上：比賽速度（`RACE_FRAMESKIP speed`） | 0.92 / 0.96 | 1.00 / 0.995 / 0.995 |
| Thor 預設配置：`collision_wait_ms` | 0.020 | 0.013 / 0.024 / 0.018 |
| Windows：`collision_wait_ms` | 0.0022 | 0.0024 |

Thor 預設配置與 Windows 的批次本來就在主執行緒到達之前做完（600 個批次裡只有 2–10 次
要等），所以沒有差別；差別在工作執行緒跑在慢核心上的手機（#176 的 Pixel 10a）。開啟後
小核心情況剩下的等待是批次的配對（`pairs_ms`，它自己一條執行緒在小核心上）與主執行緒
到達之前沒消化完的部分。

#153 的檢查（開啟，Thor，Tails 在 Dolphin Resort 的 Fly 板）：用暫時的追蹤（每格讀賽車手
`+2472` 狀態，進入 21 的下一格記下發射方向與 `+2320`）跑 9 場，一共 12 次上板（玩家 5 次、
對手 7 次，其中 3 次在小核心情況），發射方向都是板子交給的方向（`+2320` = (0.818, 0, 0.575)
或 (-0.965, 0, 0.261)），沒有一次是飛出去時的 (0,0,1) 方向；另 4 場只看截圖，也正常。
所有場次都跑到畫格上限，沒有 R6025 救援、存取違規或等待逾時。
