# 工作分派與 R6025（載入偶發崩潰）

## 原本的機制

工作分派 `823B5D40`（每格由 job system 呼叫）會：

1. 把工作項目放進無鎖佇列（`'LfQu'`：`82750B30` 判空、`82750C40` 取出）；
2. 喚醒三條輔助執行緒 `823B60C0`（處理器 1、4、5）；
3. 自己也一起消化佇列；
4. `WaitForMultipleObjects(3, done, TRUE, 16 ms)`，**不看結果**；
5. 走過 `+516` 的串列，把每個項目重設（`+160` 清旗標、`memset(+176, 0, 320)`、`+496 = 0`）後重用。

消化迴圈（`loc_823B5E30`，輔助執行緒的版本在 `loc_823B60E4`）取出項目後：

```
lwz  r11,168(r3)      ; 工作項目的函式
cmplwi cr6,r11,0
beq  cr6,<next>       ; 只擋 0
addi r4,r3,64
lwz  r5,520(r3)
mtctr r11
bctrl
```

## 症狀

`+168` 只擋 0，擋不住「C++ 基底類別的 pure virtual 欄位」。當那個欄位是純虛擬的
placeholder 時就會呼叫到 CRT 的 `sub_82A53BC0`（R6025），遊戲把它變成 `KeBugCheck`
而整個停住 —— 就是「Grand Prix 大約四次載入壞一次」的那個崩潰。

`SFR_THREAD_START_DELAY_US=0`（關掉 2 毫秒的執行緒啟動延遲）可以穩定重現：8 次裡有 2
次停住。停住當下把該項目印出來，`+168` 在 500 毫秒後變成 **0**，代表項目不是「還沒
建好」，而是**已經被第 5 步重設掉了**：分派器的等待逾時後就重用項目，而晚被喚醒的
輔助執行緒還在消化佇列。

（主機上不會發生：輔助執行緒一定在 16 毫秒內做完。這裡的輔助執行緒比較慢，還要等
執行許可，`824D0B10` 的修補已經把逾時從 16 毫秒放寬到 `SFR_WORK_SHARE_WAIT_MS`，
預設 1000。）

## 修補

`src/game_patches.cpp` 攔截 `sub_82A53BC0`，只處理那兩個呼叫點（`lr` 為 `0x823B5E88`
或 `0x823B6144`）：

- 先在**不持有執行許可**的情況下等最多 `SFR_JOB_READY_WAIT_MS`（預設 20）毫秒，讓
  還在建構這個項目的執行緒把 `+168` 填完；填好了就照常呼叫它。
- 還是空的（已經被重設）就**跳過這個項目**直接返回 —— 分派器本來就已經當它做完了。
- 兩種情況各自計數，前 8 次會印 `GAME_PATCH job_filled_in_late` /
  `GAME_PATCH job_skipped_after_reset`。

其他地方的 pure virtual 呼叫仍然交給原本的處理器（那是真的錯誤）。

2 毫秒的啟動延遲仍然保留（它讓這件事一開始就很少發生），但延遲多少才夠取決於主機
速度，手機慢得多，所以需要這個兜底。
