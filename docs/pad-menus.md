# 用手把操作選單（Kinect 語音指令）

日期：2026-09-20。分支 `claude/function-boundaries`。

先前的選單只能靠模擬的手部游標（右類比移動、停留選取），很難用。現在手把按鍵直接
對應遊戲本來就支援的 **Kinect 語音指令**，再加上一個只認手的對話框的直接選擇：

| 按鍵 | 效果 |
| --- | --- |
| START | 說「start」（標題畫面開始）；比賽與 Replay 中說「pauseopen」（開暫停選單，Replay 由此離開） |
| A | 說「ok」（選取目前的項目）；是非對話框選 ✓ |
| B | 說「back」（返回）；是非對話框選 ✗ |
| 十字鍵 | 說「up」「down」「left」「right」（轉動選單圓環、移動焦點） |
| X | 說「next」（有 Next 按鈕的頁面用；教學關的分段選單不認它，用 A） |

已驗證的流程（全程只用按鍵）：標題 START → Omochao 對話框 B（✗）→ Main Menu →
A 進 Offline Mode → 十字鍵選 Time Attack → A → 選關卡 → A → 角色選擇。
右類比的手部游標仍然可用。

## 做法

參考 GameBanana 上的 No Kinect Patch（CC BY-NC-ND，只閱讀其行為，沒有複製任何程式碼或
檔案）：它的 `TEST.dll`（以開發機金鑰加密的 XEX）在遊戲的輸入更新之後寫入語音字串。
我們依同樣的思路，在自己的 HLE 層實作：

- **輸入更新 `82494658`**（每格一次，輸入物件 = `[83E52FB8]`）：原函式先處理語音辨識器
  的結果，在 +5440 放入這一格聽到的字（UTF-16 字串指標，每格清除），+5444 分數、
  +5448 信心等級。我們在原函式之後，把**這一格新按下**的按鍵當成一個字寫入（信心 2）。
  字串放在自己映射的客體頁 `0x71720000`（在遊戲的堆積範圍之外）。
  `[83E52F8C]` 非零表示比賽中（START 改說「pauseopen」；遊戲的字表沒有「pause」）。
- **遊戲如何使用這些字**：比對用 `82A54AE0`（wcscmp）。標題畫面（`8244F880`）比對
  「start」；選單的語音表 `82434D30` 依場景（33 種）把字轉成指令編號，例如主選單
  `offlinemode`、`option`、`shop`，通用詞彙 `up`/`down`/`left`/`right`/`back`/`ok`/
  `on`/`off`/`hai`/`iie`/`shop_buy`，以及關卡、角色、裝備名稱。
- **只認手的對話框 `823EF348`**（對話框, 手）：傳回手停留夠久的按鈕欄位 0..2，沒有則 3。
  標題的 Omochao 對話框與另外兩處使用；+124 是版面，4 = 欄位 0（是）與 1（否），
  3 = 欄位 2 單一按鈕。語音對它無效，所以按下 A／B 時直接傳回欄位，並用原函式的
  `8222FA18` 播放確認（16）／取消（8）音效。
- 遊戲只在手部游標存在時（`[83E52F7C]+12`）才呼叫這個對話框函式，所以玩家被辨識後，
  模擬的右手會自動舉起並**停在左上角**（約 60, 50，沒有按鈕的位置）。

每個玩家資料 +3034 的位元組是「語音輸入可用」；為 0 時原本的更新不處理語音辨識，
但標題與選單讀字的路徑不受影響，所以不需要改它。

## 驗證

```bash
SFR_SKIP_MOVIES=1 SFR_INPUT_AFTER_PRESENT=1800 SFR_INPUT_PRESENT_CLOCK=1 \
SFR_INPUT_SCRIPT="start@3+0.2,b@21+0.2,a@35+0.2,right@45+0.2,a@52+0.2,a@62+0.2" \
out/build/host/sfr_cpu_diagnostic.exe out/recomp/image-loader private/assets --game-region=ntsc-us
```

記錄中有 `NUI_SPEECH word=...` 與 `NUI_DIALOG_CHOICE ... slot=1`。
`SFR_INPUT_PRESENT_CLOCK=1` 讓腳本的秒數以 60 格畫面計算（不受主機速度影響）；
沒有它時是實際秒數，而遊戲比實際時間慢，按得太早時對話框還沒出現。

另外：十字鍵左右會轉動環狀選單（8246A6D0 的滑動量），B 會用該頁的返回按鈕，
Y 會按下商店捷徑按鈕（類型 33..35）。用「ok」選了環狀項目之後，若換頁的延遲動作
停住不動，會像手離開按鈕一樣放開該按鈕（824574D0）。

## 語音詞彙從哪裡來

映像裡的 UTF-16 字串（`0x821A84D8` 一帶）就是選單的通用詞彙：
`up`／`down`／`left`／`right`／`on`／`off`／`shop_buy`／`next`／`restart`／`replay`／
`mainmenu`／`courseslc`／`ruleslc`／`gearslc`／`charaslc`／`playernumslc`／`missionslc`／
`tutomission`／`networkmenu`／`resi_*`，加上 `0x8219EA1C` 的 `ok`、`back`、`pauseopen`。

`SFR_SAY="word@present,..."` 可以在指定的 present 說出任何一個字，用來找出某一頁到底
認哪個指令，不必為每個猜測加一個按鍵。

## 裝備零件畫面為什麼曾經停住（已修正）

2026-09-21 修正。症狀是兩個插槽放滿之後畫面就不再前進，任何語音指令都沒有用。
先前記在這裡的推論有兩處是錯的，一併更正：**選單更新在這一頁一直有被呼叫**，而
`[r3+436]` 是空的只是因為根本還沒走到建立它的那個狀態。

選單管理器（`824578F0`，`r19 = manager+36`）依 `[r19+4]` 分派，實際的狀態是 2..6：

| 狀態 | 進入點 | 做什麼 |
| --- | --- | --- |
| 2 | 看 `[r19+1824]` | 為 0 就直接把狀態加一 |
| 3 | `loc_82457ACC` | 狀態加一 |
| 4 | `loc_82457B30` | **正常執行**：每格呼叫 `82456D60` → `82456700` |
| 5 | `loc_82458450` | 兩個玩家插槽都鎖定且佇列清空時，建立換頁淡出物件寫進 `[r19+436]` |
| 6 | `loc_82458560` | 等 `[[r19+436]+20] == 3`，然後 `8245E6B0` |

卡住的是**狀態 5**。它要 `82452F48(r19+1828 + 88*n)` 對兩個玩家都傳回非 0，而
`82452F48` 只在插槽的 `[+20] == 0` 時鎖定 `[+59]`。實測（`SFR_MENU_STATE=1`）：

```
NUI_MENU_LEAVE queue=... first=0 last=0
  | slot0 p20=10 b56=0 b57=0 b58=0 b59=0     ← 玩家 1 卡住
  | slot1 p20=0  b56=0 b57=1 b58=0 b59=1
```

`[+20]` 是插槽自己的狀態機 `82491458` 的狀態（`SFR_WATCH_WORD` 指認出來的）：

1. **狀態 9**（`loc_82491B10`）呼叫 `82233470` → `824D0CB0` → **`XamShowNuiSigninUI`**，
   然後設成狀態 10。
2. **狀態 10**（`loc_82491B30`）等 `[[0x83E52F6C]+32541]` 變成非 0 才前進。
3. 那個位元組由 `82233040` 設定 —— 遊戲的 `XNotifyGetNext` 抽取迴圈，收到
   **`XN_SYS_UI`（id 9）** 時把參數寫進去。

我們的 `XamShowNuiSigninUI` 原本一次送出 `XN_SYS_UI(1)` 和 `XN_SYS_UI(0)`，而遊戲的
抽取迴圈**一次呼叫就把佇列抽乾**，所以那個位元組在同一次呼叫裡 1 → 0，狀態 10 永遠
看不到「UI 顯示中」。修正是在 `NativeNotifications` 加上 `publish_when_drained()`：
項目要等該監聽者回報過一次空佇列才加入，所以「關閉」一定落在下一次抽取。這也比較
接近真機 —— 系統 UI 不會在同一格開又關。

修正後的記錄：

```
NUI_MENU_STATE frame=9480 state=4 action=1 elapsed=23 waited=0x0
NUI_MENU_STATE frame=9499 state=5 action=0        waited=0x0
NUI_MENU_STATE frame=9500 state=6 action=0        waited=0xfee2bbd0 waited20=2
```

### 附帶調整

- `enter_function` 裡那個 inline mip 稽核原本硬性要求「下一個進入的原始函式是
  `0x8222BDB0`」。橋接函式的最後一個呼叫就是被稽核的那次，之後它就返回了，所以下一個
  進入的是**呼叫者**接著呼叫的東西。稽核真正要驗證的取樣器狀態完全保留；同一趟
  10567 次裡 10563 次仍是 `0x8222bdb0`，4 次是別的，而狀態檢查全部通過。
- up draw 收集頂點的理智上限從 1 MB 提高到 8 MB：比賽一次就會畫 56913 × 20 位元組。
