# 整個遊戲停住的死鎖

## 症狀

關掉執行緒啟動延遲（`SFR_THREAD_START_DELAY_US=0`）跑 Free Race，**三輪裡有兩輪會在
同一個 present（10602）完全停住**：48 條執行緒全部處於等待狀態、CPU 沒有任何消耗、
log 不再增加。放著三小時也不會恢復。

## 為什麼看門狗說不出話

看門狗在逾時前一秒會要求每條客體執行緒印出堆疊，但那是在**函式進入點**做的。完全
死鎖時沒有任何執行緒會再進入函式，所以什麼都不會印 —— 一個掛了三小時的執行，log
裡一個字也沒有。

因此新增了 `SFR_HANG_SECONDS=N`（`src/diagnostic_main.cpp`）：只要 N 秒內沒有新的
present，就印出

- `HANG_THREAD`：每條還沒結束的客體執行緒目前在哪個 import、是否在原生等待中；
- `HANG_PERMIT`：全域與每個核心的執行許可**由誰持有、誰在排隊、誰在等待中**。

報告一行就把範圍縮到很小：

```
HANG_PERMIT scope=global owner=1 ready=18,16,11,25, blocked=5,6,13,...
HANG_THREAD guest_id=1 blocked=0 in=guest code
```

**主執行緒持有全域許可**、不在任何 import、也不在原生等待裡 —— 它卡在我們自己的某個
hook（hook 不算 import），而每個核心許可都沒人持有。

## 真正的原因：貼圖上傳的暫存緩衝區被太早釋放

同一天為了效能做的改動（docs/performance.md）讓貼圖上傳**不再等待 GPU**，並把暫存
緩衝區改成「兩格之後釋放」，理由是退休的頂點緩衝也是這樣。那是錯的：那些緩衝區是被
**另一條提交**（上傳的命令清單）讀的，跟畫面格數沒有關係。GPU 還在讀時記憶體就被回收，
於是那次提交的 fence 永遠不會 signal，主執行緒就握著許可永遠等下去，其他人再全部卡在
它後面。

`SFR_TEXTURE_UPLOAD_WAIT=1`（回到舊的逐次等待）跑 4 輪全部正常，確認了是這條路。

## 修法

每個上傳槽（四個輪替的命令清單之一）**自己持有它那次提交的暫存緩衝區**，只有在等到
該槽的 fence 之後才釋放。這樣在定義上就不可能太早放掉 GPU 還在讀的記憶體。

順帶修掉的另一件事：`GuestExecution::wait_until_ready()` 原本會**持有許可無限期等待**
被喚醒的執行緒進入就緒佇列。目標若當下正在自己的等待中，它得先醒來才會就緒，而那往往
要等擁有者繼續跑 —— 這是另一個可能成環的地方。現在目標已在等待中就直接返回，並加上
50 毫秒的有界等待，逾時次數由 `GuestExecution::resume_wait_timeouts()` 計數（正常執行
是 0，死鎖報告會印出來）。

## 驗證

`scratchpad/hang2.sh`（= `repro.sh` 加上 `SFR_HANG_SECONDS=30`），關掉啟動延遲：

| | 結果 |
| --- | --- |
| 修正前 | 3 輪裡 2 輪在 present 10602 停住 |
| 只還原上傳等待（`SFR_TEXTURE_UPLOAD_WAIT=1`） | 4/4 跑完 |
| **修正後** | **6/6 跑完，零死鎖** |
