# Toolchain notes

The verified host is Windows x86-64: Visual Studio Community 2022 17.9.4 SDK environment, LLVM 21.1.8 (`clang-cl`), CMake 4.2.3 and Ninja 1.13.2. Android NDK r29-beta2 (29.0.13599879-beta2), Clang 20.0.0, now cross-compiles and links the ten standalone runtime test executables for ARM64/API26; no device run or APK is claimed (see `android-core.md`). Java 21 was found but was not used for packaging.

`scripts/build_tools.ps1` imports `vcvars64.bat` into the current process, configures CMake/Ninja under `out/build/host`, and explicitly selects independent LLVM. `-DCMAKE_POLICY_VERSION_MINIMUM=3.5` permits the upstream old CMake minimum declarations with CMake 4; upstream deprecation warnings remain. No upstream source patch was required.

The diagnostic builds in Release using the compiler's release optimization setting, strict floating-point mode, no strict aliasing, and Sandy Bridge instructions on x86-64, matching the general target architecture of the references. Generated translation units use checked scalar memory, indirect-call, clock, bounded reservation and full-vector/word-store memory hooks. Unrecognized raw vector/atomic bodies and known translation hazards still stop; this is conservative containment, not full instruction verification.

All configuration paths passed to the pinned XenonRecomp must be relative to the generated TOML directory. Its implementation concatenates directory strings and does not correctly handle absolute values for `file_path` or `out_directory_path`. The reproducible driver handles this constraint. An initial failed run is preserved locally as `out/recomp-failed-paths`; its status explicitly says incomplete.

On Windows, the XEX and output directory must be on the same drive. The driver checks this before reading the source or creating output; extract or copy the XEX into the project first when the original is on another drive.

`prepare_recomp.py` produces a new run directory containing:

- `image/`: decoded image, original `xex_header.bin`, sections, function imports, variable imports and completion marker.
- `switches.toml`, `analyse.log`: exact analyzer output. The current analyzer finds zero tables; this does not establish that the game has no switches.
- `recomp.toml`, `recompile.log`, `ppc/`: exact game configuration, all raw diagnostics, and unmodified generated C++.
- `diagnostic/`: audited diagnostic copy, import stops and per-function report including source and generator fingerprints.
- `status.json`: completion of diagnostic generation, explicitly `playable: false` and `raw_translation_complete: false`.

The native tools guard the supported input before calling the upstream image parser. Source intake uses SHA-256; the image dump and diagnostic additionally use fixed SHA-1 fingerprints to detect accidental input mismatch with the exact locally verified source and decoded output. These are supported-version checks, not a general authentication service.

Other desktop platforms can use the root CMake project for porting work, and the ten standalone runtime core tests now pass under Arch Linux/WSL2 with GCC 14.2.1 and 4 KiB pages (see `linux-core.md`). The complete generated diagnostic and macOS build have not been tested. Android/iOS packages are not completed platform support. The observed initialization path now includes loader, memory, process/hardware, critical sections, privileges, TLS, clocks and bounded word reservations. Full-vector static initializers now run; the original caller handles an explicit non-success Etx policy. Startup now passes native memory accounting, two current-display queries and a real 0x7203000-byte physical allocation. A real write-combined allocation follows. Startup stops on VdInitializeEngines at0x82ACBC2C (1,271 function entries). Plain subfze translation enabled entry into sub_82211798. The instruction itself is later in that function and has not been observed executing on this boot; see `integer-arithmetic.md`. Original code now handles six explicitly absent native party/community exports; see `party-export-policy.md`. See `native-modules.md` for the bounded loader contract. This policy does not implement tracing; see `etx-investigation.md`. Instruction/function analysis and gameplay backends remain incomplete. Contracts are in `xex-loader.md`, `virtual-memory.md`, `process-heap-init.md`, `hardware-info.md`, `critical-section-locking.md`, `thread-local-storage.md`, `system-time.md`, `timestamp-clock.md`, `reservations.md` and `vector-memory.md`; the complete diagnostic is verified only on Windows; standalone core tests also run on the documented Linux environment.

Existing diagnostics generated before the loader increment must be regenerated: the host now uses `dispatch_import`, and image dumps must contain the verified original header. This workspace preserves its earlier outputs and uses `out/recomp/image-loader` and `out/recomp/diagnostic-subfze`; see README for commands.

Windows directory publication can briefly fail with access denial after files close. Controlled local probes observed 20 WinError 5 occurrences across 1200 diagnostic tests, all resolving after 50 ms. The generator now retries only Windows errors 5/32/33 for at most five rename attempts, waiting 50 ms between attempts, and stops immediately if the destination appears. Persistent and non-Windows errors still fail. This keeps directory publication atomic; no output is overwritten and no translation content is changed. The locking process was not identified. Synthetic fixtures now live under ignored `out/test-tmp`; relocation alone was insufficient to eliminate the observed issue.

Windows GuestMemory now requires VirtualAlloc2 placeholder support, resolved dynamically from KernelBase. Separate private replacement allocations preserve per-range normal or write-combined cache attributes within the4GiB guest window. Missing API support stops explicitly; this increment was tested on the current Windows host, not on additional Windows versions or other platforms. See `write-combine.md`.

Windows builds also link pinned Plume from `tools/Plume`; run bootstrap after updating the lock. The diagnostic initializes its D3D12 device/queue at the observed game graphics boundary; no window or game draw is implemented yet. Full Windows CTest now includes a hardware GPU upload/copy/readback test with a 20-second timeout. The current system SDK builds this Plume revision with Agility disabled; other hosts do not build this Windows owner/test. See `native-graphics.md`.
